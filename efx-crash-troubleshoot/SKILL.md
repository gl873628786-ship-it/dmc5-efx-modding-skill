# EFX 崩溃与失效排错

## R — 原文 (Reading)

> `*ERROR Line 2432：模板读取超出文件末尾`
> `*ERROR Line 153：模板读取超出文件末尾`

— 视频分 P 02 [01:21]、分 P 04 [00:46]（画面文字 OCR）

> 有个要注意的点是，在开着游戏的时候换了序列动画的话，在关卡中有时候重新加载本关无法刷新，需要退到主界面重新选关进游戏才行。

## I — 方法论骨架 (Interpretation)

排错的第一件事不是看报错内容，而是**先判断这次故障走的是哪条通道**。EFX 编辑只有三条通道，各自的根因完全不同：

**通道 A — 解析期报错（模板抛 `*ERROR`）**
模板是**照着 Header 声明的长度往下读**的。所以 `模板读取超出文件末尾` 的含义永远是固定的：**某处声明的数字 > 文件里实际的字节数**，而不是"报错那一行有问题"。
两把钥匙是把**报错行号的量级**当成层级指示器：
- 行号是**四位数**（如 2432）→ 优先怀疑**文件级**计数：Effect Count。文件大了几千行说明结构体量大。
- 行号是**三位数**（如 153）→ 优先怀疑**某个 Effect 局部**的计数：Segment Count。

**通道 B — 静默失效（改了没反应，但不报错）**
根因是"值域非法"或"引用断裂"，不在结构一致性上。按危害排序依次查：
① Min/Max 区间非法（Max < Min+1）→ 这个通常会崩而不是静默；
② 引用链断了（uvs 没放对路径 / uvs 里的 tex 路径没改 / 彩色图没改 tex_light）→ 最常见；
③ 选错了层（大小改在 Type* 段但 Transform3D 是 1 以外的值，两处相乘）→ 表现为"尺寸离谱"；
④ 该段本来就不生效（RotateAnim 没挂在渲染段上；MeshEmitter 没配 GpuBillboard）；
⑤ 约束不允许（GpuBillboard 想单轴缩放）。

**通道 C — 运行期不刷新（结构对了、值也对，但游戏里还是旧的）**
这是**缓存**问题，不是文件问题。已知例外：热替换序列帧动画后，关卡内重载本关有时不刷新，**必须退到主界面重新选关**。判断标志是"其他改动都能生效，唯独这次不生效"。

排错的正确顺序是 **A → B → C**：先确认模板不报错（结构自洽），再确认引用与层选对（逻辑自洽），最后才怀疑缓存（环境）。

## A1 — 源素材中的应用 (Past Application)

### 案例 1：删特效组后忘改 counts

- **问题**：删掉一段特效组结构后，变量树立刻变红并抛出 `*ERROR Line 2432`。
- **方法的使用**：不理会报错行号对应的内容，而是回头看"我刚才删了什么结构" → 回到 EFX Header 把 Effect Count 减 1。
- **结论**：报错是"声明长度与实际长度脱钩"的信号，而不是"第 2432 行写错了"。
- **结果**：计数补上后 ERROR 消失，结构恢复自洽。

### 案例 2：粘贴属性后报 Segment Count 错误

- **问题**：给基础纹理特效粘贴了 ScaleAnim 段，立刻报 `*ERROR Line 153`。
- **方法的使用**：注意到行号只有三位数（对比案例 1 的四位数），判断这是**局部计数**而非文件级计数 → 检查该 Effect 的 Segment Count。
- **结论**：报错行号的量级本身就是"错误在哪一层"的路标。
- **结果**：确认是 Segment Count 未加 1；这次故障成为"用行号量级分层"这条推理法的证据来源。

### 案例 3：序列帧动画热替换不刷新

- **问题**：游戏运行中把 8×8 烟雾序列帧换成 8×8 火焰，模型能换、结构也不报错，但游戏里重载关卡始终是旧动画。
- **方法的使用**：先确认模板无 ERROR（通道 A 排除）、再确认 uvs 路径与 tex 路径都已同步（通道 B 排除），剩下只可能是缓存。
- **结论**：这是"改完保存重进关卡即生效"的**已知例外**，需要退到主界面重新选关。
- **结果**：退主界面重选关后新动画正常显示。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill？

1. 改完 efx 保存后**游戏直接崩了**（进关卡就退、黑屏）。
2. 010 Editor 里**模板报错**（`*ERROR Line xxxx`、变量树变红、解析到一半停住）。
3. 改完文件**完全没反应**，游戏正常运行、特效就是不变。
4. 改完**部分生效**（比如特效出来了但贴图不对、颜色不对、尺寸离谱）。
5. 改的是**序列帧动画**，重进关卡多次都不刷新，怀疑自己改错了。

### 语言信号（用户的话里出现这些就应激活）

- 中文：「改完游戏崩了」「一进关卡就闪退」「模板报错了」「读取超出文件末尾」「改了没反应」「改完没效果」「进游戏还是原来的样子」「重进关卡也不刷新」
- English: "the game crashes after my edit", "template read past end of file", "my change has no effect", "it still shows the old animation", "010 Editor shows an error"

### 与相邻能力的区分

- 与 `efx-safe-structure-edit` 的区别：那个是**预防与修正动作**（增删时怎么同步数字）；本能力是**故障发生后的诊断路径**（先分流通道，再定位根因）。本能力的输出常常是"回到 `efx-safe-structure-edit` 去补一个计数"。
- 与 `efx-numeric-semantics` 的区别：本能力负责**发现**"是数值违规"，具体"该怎么填"交给那个。
- 与 `efx-edit-hygiene` 的区别：那条讲的是开工前的纪律；本能力是出事之后的流程。

## E — 可执行步骤 (Execution)

1. **分流：报错、静默、还是缓存？**
   - 010 Editor 里有 `*ERROR` 或变量树解析失败 → **通道 A**
   - 模板干净、游戏不崩，但效果不对/没有 → **通道 B**
   - 一切正确，只是画面还是旧的 → **通道 C**
   - 完成标准：明确说出故障属于哪条通道。

2. **【通道 A】按声明长度 vs 实际长度找缺口**
   - 先回想"我刚才增删/改长了什么"。
   - 看报错行号量级：四位数 → 查 `Effect Count`；三位数 → 查该 Effect 的 `Segment Count`。
   - 若是内嵌 efx 或长字符串，查对应的 size（`Path/EFX size`、`pathsize`、骨骼名 size、Condition Block size）。
   - 修完按 F5 重解析。
   - 完成标准：`*ERROR` 消失，变量树解析完整。
   - 判停条件：若确认所有计数与长度都已对齐却仍报错 → 说明文件已被覆盖损坏（见边界），从备份重来。

3. **【通道 B】按"值域 → 引用 → 层选 → 依赖 → 能力"顺序筛**
   - 值域：是否动了任何 Min/Max 且 Max < Min+1？（→ 崩溃或异常）
   - 引用：改的是贴图/模型吗？efx → uvs → tex 三跳路径是否都改了？uvs 文件是否放到了新路径？彩色图是否改了 tex_light？
   - 层选：是不是同时改了 Transform3D 和 Type* 的大小（两处相乘）？
   - 依赖：RotateAnim/ScaleAnim 有没有挂在渲染段上？MeshEmitter 有没有配 GpuBillboard？PtLife 的跟随有没有开 ParentOptions 的 FollowBone？
   - 能力边界：是不是要求了 GpuBillboard 做逐轴缩放、MeshEmitter 配非 GpuBillboard？
   - 完成标准：定位到一个具体原因并说明它的机制。
   - 判停条件：若以上全否，转通道 C 或检查环境（路径是否含中文）。

4. **【通道 C】排除缓存**
   - 若改动涉及序列帧动画（uvs/tex）→ 保存后**退出到主界面，重新选关**进游戏。
   - 完成标准：新效果出现。
   - 判停条件：仍不出现 → 回到步骤 3 重新怀疑引用链（很可能是 uvs 里的 tex 路径没改）。

5. **回写教训**：把这次根因归类（计数 / 长度 / 值域 / 引用 / 层选 / 依赖 / 缓存），下次同类改动前先自查。
   - 完成标准：能用一句话说出"这次的根因是 X 类"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 还没做任何改动、只是想知道"改之前要注意什么" → 用 `efx-edit-hygiene` 和 `efx-safe-structure-edit`，本能力是事后用的。
- 问题出在 3DS Max / Noesis / MOD 管理器等**外部工具链**上（不是 efx 文件本身）→ 不属于本能力的范围。
- 故障发生在**另一个 RE Engine 游戏**上 → 报错格式与计数布局可能不同。

### 源素材中警告的失败模式

- **把报错行号当"出错的行"去改**：模板是按声明长度跳读的，报错行与真正的错误位置没有直接对应，盯着它改会越改越乱。
- **数据已被静默损坏**：粘贴前没重新定位而覆盖了蓝色高亮选区时，损坏不会立刻报错，可能直到进游戏才暴露；这种情况下"补齐计数"救不回来，只能回备份。
- **把"静默失效"当成"结构错误"**：反复去 F5、反复查计数，方向全错——静默失效几乎从不来自结构不一致。
- **把缓存问题当成文件问题**：反复重做同一个改动，越改越怀疑自己。

### 作者的盲点 / 局限

- 作者对崩溃原因多处标注 **"原因未知"**。这意味着本能力的排查清单是**经验排序**，不是因果推导：能给"先查什么"，不能保证"一定是这个"。
- 序列帧刷新例外，作者原话是"**有时候**"不刷新——连作者也不确定触发条件。因此通道 C 只能作为兜底，不能作为首选假设。

### 容易混淆的邻近方法

- **"模板报错" ≠ "游戏崩溃"**：前者是解析期、可以在编辑器里发现；后者是运行期、只能进游戏才知道。二者的根因不同，不要用一个的排查法去套另一个。
- **"改完没反应" ≠ "改错了"**：可能只是没退主界面重选关（通道 C）。
