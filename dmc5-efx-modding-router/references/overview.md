## 1. 结构 (Structural)

### 类型

**逆向工程导向的实操手册**（面向游戏引擎二进制资源文件的手工编辑），不是理论书。核心是"文件结构认知 + 编辑纪律 + 属性语义表"。

### 一句话主旨

把《鬼泣5》(RE Engine) 的二进制特效文件 `.efx` 用 010 Editor 的模板解析成可读的数据结构，然后靠"**复制段 → 粘贴段 → 同步计数 → 按 F5 重解析**"这一套固定动作，在**不写一行代码**的前提下安全地增删特效组、增删属性、改贴图/模型路径、绑骨骼、加触发条件。

### 骨架（主要论点及其关系）

1. **结构模型层**：`.efx` = EFX Header（若干 count 元数据）+ Name Buffer + Linked/Embedded EFX + Effect[]；每个 Effect 由若干 Segment 组成；TypeMesh 额外有 Override Hash。→ 一切编辑都是对这个结构的增删改。
2. **一致性不变量层**：任何结构增删都必须同步三类数字 —— ① **计数**（Effect Count / Segment Count / Linked EFX Count / Override Hash Count / Condition Block Count）② **字节长度**（Path/EFX size、Condition Block size、骨骼名 size）③ **排序**（Segment 按 Id 升序，冲突时 Id 大者覆盖小者）。
3. **属性语义层**：每类 Segment 管一个维度 —— Spawn（生成节奏）、Life（存活时长）、Transform3D（整体变换）、ParentOptions（骨骼跟随）、RotateAnim / ScaleAnim（动画）、Velocity3D（运动）、EmitterShape3D（空间散布）、Distortion（扭曲）、PtLife / PtCollision / PtColliderAction（触发）、MeshEmitter（网格发射）。
4. **渲染类型层**：TypeBillboard3D（永远朝摄像机）、TypePolygon（不朝摄像机、可三轴旋转）、TypeMesh（贴 mdf+fbx 的静态网格/顶点动画）、TypeGpuBillboard（海量粒子）、MeshEmitter（按网格顶点撒粒子）。→ 决定"长什么样"，且**必须与纹理类属性（UVSequence）搭配**。
5. **资源引用层**：贴图链路 = `efx → UVSequence → uvs 文件 → tex 文件`；模型链路 = `TypeMesh → mdf + fbx`。改路径要同步改 size，且要维持后缀名/网格数约定。
6. **验证工作流层**：010 Editor + bt 模板 + 游戏内实时预览（辅以 EMV 引擎/无人机工具拉镜头）；"改完保存 → 重新进关卡即可生效"（个别情况需退主界面重选关）。

**论点之间的关系**: **层层递进 + 依赖**。2 依赖 1（不懂结构就不知道要同步哪个数）；3/4 并列，同属"编辑内容"；5 是 4 的延伸（类型决定了要挂什么资源）；6 是贯穿全部的执行回路。

### 作者要解决的核心问题

**"为什么我改一个特效文件，游戏就崩 / 就不生效？"** —— 以及在此前提下，"一个非程序员的 MOD 作者，怎么建立一套可重复、可排错的手工编辑流程"。

## 2. 解释 (Interpretive)

### 关键术语（作者本人的用法）

| 术语 | 作者的定义 | 和常识用法的差异 |
|---|---|---|
| EFX 文件 | RE Engine 的特效定义文件，二进制，靠 `.bt` 模板（010 Editor 脚本）解析后才有名字 | 不是"特效资源"而是"特效的**结构描述**"；贴图、模型都外链 |
| Effect（特效组） | 文件里一个独立的效果单元，有自己的名字（如 light、aura、Trajectory color 15） | ≈"一个特效"，但它是**容器**，内部还有 Segment |
| Segment / Attribute / Property | 特效组内部的属性段，三者是同层级的不同叫法 | 不是"属性值"，是**一段有类型 ID 的二进制结构** |
| Id / Item Type ID | Segment 的类型编号（如 `2Ch` = Life、`3Ch` = Distortion），决定排序与冲突优先级 | 不是"序号"，是**类型码**；Id 大者覆盖小者 |
| Range | `XxxRange` 字段：最终值 = 基准值 ± Range，即"浮动范围" | ≠ Min/Max 区间，两者机制不同 |
| Min / Max | 取值在 [Min, Max] 内随机 | **Max 必须比 Min 大 ≥1，否则游戏崩溃**（都是 0 除外） |
| Linked vs Embedded EFX | Linked 是外链别的 efx（改体积不用改 size）；Embedded 是内嵌（改体积必须同步 Path/EFX size） | 作者**明确推荐 Linked**，纯因为 Embedded 的维护成本 |
| cond / Condition Block | 特效的触发限制条件（人类条件下、魔人条件下、拿在手上条件下） | 不是脚本条件，是**数据结构里的条件表**；`ukn=2` 表示无限制 |
| ukn / 不明的值 | 作者对语义未确定的字段的标记 | 作者**公开承认不确定**，这是本教程可贵的诚实，也是其边界 |
| uvs 文件 | 序列帧纹理的"帧→坐标"映射表 | ≠ 贴图；uvs 里存着**每一帧的 UV 坐标**，所以换动画时网格数（如 8×8）要匹配 |

### 核心命题（用自己的话）

1. **EFX 编辑的本质是"结构编辑 + 计数同步"，不是"调数值"。** 数值改错了顶多没效果，计数或字节长度没同步会直接崩或让模板解析爆掉。
2. **崩溃几乎总能归因到"两处数字不一致"**：`*ERROR Line xxxx: 模板读取超出文件末尾` 就是"header 里声明的长度 > 文件实际长度"。
3. **Min/Max 与 Range 是两套随机机制，不能混用**：见 Min/Max 就是区间随机；见 Range 就是"基准值 ± Range"随机。
4. **类型段决定外观，纹理段决定皮，动画段决定动，变换段决定在哪/多大/朝哪。** 想改什么，先定位到管这件事的那一层。
5. **大小/缩放有两个可改的地方（Transform3D 与 TypeXxxx），必须把一边设成 1 再改另一边**，否则两处相乘，结果失控。
6. **旋转一律填弧度**（90° = 1.57079），位置和旋转可以是负数，缩放不行。
7. **动画类属性（RotateAnim / ScaleAnim）本身不产生效果，必须挂在一个纹理或网格类型上**；加速度 = 1 是匀速，<1 减速到停，>1 加速到消失。
8. **粒子与网格类属性对"数量/顶点分布"敏感**：MeshEmitter 的粒子分布完全由网格顶点决定；TypeGpuBillboard 不受 ScaleAnim 单轴缩放影响。
9. **所有资源路径都可以短化到"以 vtx/vfx 文件夹开始"并保留后缀名（如 `-uvs`）**，这样 MOD 可以打包分发而不依赖绝对路径。
10. **改前备份是一等纪律**：卸载 MOD 会删掉游戏根目录的 `natives` 文件夹，改好的文件必须提前复制出来。

### 论证链

作者的论证方式不是"推理"，而是**"演示 → 观察游戏内结果 → 归因"** 的实证循环：

- 每节课固定套路：打开示例 efx → 在 010 Editor 里改一个东西 → 保存 → 进游戏看效果 → 用画面上的浮层字幕指出"这就是我改的那个字段造成的"。
- 反例（崩溃）同样是演示出来的：故意不同步计数，看到 `*ERROR Line 2432`，再补上就正常 —— 用**故障现象反推不变量**。
- 术语与字段名全部来自 010 Editor 模板的变量树（如 `Effect Count`、`ItemType_UVSequence (2Eh)`），因此**字段名即事实来源**，不靠记忆。

## 3. 批判 (Critical) ★

### 作者的时代局限

- **强绑定特定工具版本与模板版本**：010 Editor v11.0.1 汉化版 + 特定 `DMC5_EFX.bt` 模板。模板一旦更新（字段增删），视频里"第几行第几列"的操作与字段偏移就会失效。
- **强绑定特定游戏版本/patch**：示例用 `pl0800`（维吉尔 DLC 后的玩家特效）、`re_chunk_000.pak.patch_005`。后续官方 patch 会移动资源与结构调整。
- **RE Engine 各作不通用**：本教程只讲 DMC5；RE2/RE3/RE4/MHR 的 efx 属性表不同，照搬会错。
- **依赖"游戏内预览"这一唯一验证手段**，没有任何离线校验器 —— 反馈慢且有风险（崩游戏）。

### 作者的立场盲点

- **只讲"怎么做"，不讲"为什么"**。所有不变量都是经验归纳（"否则游戏崩溃（原因未知）"），没有引擎层面的解释。这使知识**不可外推**：模板没覆盖的新属性就无从下手。
- **知识盲区被如实标注，但比例不低**。EmitterShape3D 的 12 个值"好像只有编号 0 有影响"、Velocity3D 的 ukn 系列、Spawn 的完整机制、PtCollision 的 ukn8~11 —— 大量字段语义是"猜"的。这些"猜测"如果被下游 skill 当成确定知识，会造成误导。
- **面向"有美术基础的人"**：默认你会 3DS Max、会 Noesis、会做贴图。跳过模型/贴图的生产环节，只教"怎么塞进去"。
- **无工程化意识**：纯手工二进制编辑、无版本控制、无 diff、无回滚，唯一防线是"自己复制一份备份"。

### 未被证明的假设

- 假设"模板变量树里的字段名 = 引擎里的真实语义"。实际上模板是社区反推的，字段名可能命名不准（如大量 `ukn`）。
- 假设"改完文件保存 → 重新进关卡即可生效"。这是观察到的现象，但不是机制；视频自己也遇到"换序列帧动画时必须退主界面重选关"的例外。
- 假设"Id 大者覆盖小者"的冲突规则普遍成立，但作者只在一个场景（Transform3D vs TypeXxxx 的大小）演示过。
- 假设"Segment 排序不影响功能"（p04 明说"属性排序有无影响暂且不明"）—— 而同一教程又建议按 Id 排序，**内部存在张力**。

### 最强反对意见

**"这套方法的上限是"复刻+微调"，不是"创造"。** 因为它依赖社区模板去解析二进制，任何模板未覆盖的结构都无法编辑；且作者自认大量字段语义不明，意味着**真正的自由度被"猜测的边界"锁死**。若要反驳，会说：与其手工改二进制，不如直接写 RE Engine 的 efx 导出插件，从工具链层面解决——但这需要逆向工程能力，超出了本教程的目标读者。

## 4. 应用潜力 (Applicability)

### 可 skill 化的内容

- [ ] **安全增删特效组/属性的固定动作**（复制→粘贴→同步计数→F5 重解析→进游戏验证）
- [ ] **计数与字节长度同步清单**（Effect Count / Segment Count / Linked EFX Count / Override Hash Count / Path size / Condition Block size / 骨骼名 size）
- [ ] **崩溃排错**：从 `*ERROR Line xxxx` 反推"哪两处数字不一致"
- [ ] **属性选型决策**：想改"时长/位置/大小/运动/散布/透明度/触发"分别该去哪个 Segment
- [ ] **渲染类型选型**：朝不朝摄像机、要不要挂模型，决定用 Billboard3D / Polygon / Mesh / GpuBillboard
- [ ] **纹理资源链路改造**（efx → UVSequence → uvs → tex 的路径与 size 同步，序列帧网格数匹配）
- [ ] **模型资源链路改造**（TypeMesh 的 mdf + fbx 替换，子网格数 = FrameCount）
- [ ] **骨骼跟随配置**（ParentOptions 十个 0/1 开关 + FollowBone + 骨骼名写入与 size 同步）
- [ ] **条件触发配置**（ukn 0/2 语义、Condition Block 结构、按条件触发的特效）
- [ ] **数值语义速查**（Min/Max vs Range、弧度换算、加速/减速/匀速判据、负值方向）
- [ ] **编辑前备份纪律**（natives 文件夹、卸载 MOD 会删目录）

### 不适合 skill 化的内容

- 具体鼠标/快捷键演示（Ctrl+Shift+C/V、F5、Ctrl+Shift+I 的具体点击轨迹）→ 作为 E 段里的步骤细节保留，不独立成 skill
- 3DS Max 建模流程本身（导 FBX、摆位置、改名的美术操作）→ 作为 example 保留
- 游戏内跑图验证的录像 → 纯演示，无方法论
- RE Engine 各游戏的对比 → 仅作为 Boundary

### 预估 skill 数量

**约 6–9 个**（最终由阶段 1.5 三重验证 + 1.6 晋级门决定，这里只是粗估）

### 优先级排序（按"最能赋能普通人 / 最容易踩坑"的角度）

1. **安全增删与同步不变量**（不学这个必崩，且是全部编辑的前置）
2. **崩溃排错：从 ERROR 反推不一致**
3. **属性选型决策表**（把 20+ 个 Segment 压成"想改 X 就去 Y"）
4. **渲染类型选型**（Billboard3D / Polygon / Mesh / GpuBillboard / MeshEmitter）
5. **贴图链路改造**（UVSequence + uvs + tex，最高频的改皮肤需求）
6. **模型替换链路**（TypeMesh + mdf + fbx + 子网格/帧数对应）
7. **骨骼跟随 + 条件触发**（进阶，但决定了特效能不能"长在角色身上""只在特定状态出现"）
8. **数值语义与单位速查**（弧度、帧、nits、Min/Max vs Range）
