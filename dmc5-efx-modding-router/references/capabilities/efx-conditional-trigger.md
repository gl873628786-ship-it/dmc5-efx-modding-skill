## I — 方法论骨架 (Interpretation)

"特效什么时候出现/消失"由**三类互不相同的触发机制**决定。它们的配置位置、作用时机都不同，混用会互相抵消。

**第一类：状态条件触发（文件里的"条件索引表"）**
- `uint32 ukn`：**0 = 只在特定条件下触发；2 = 无限制条件**。（注意：**2 不是"2 个条件"**，只是"无限制"这一档。）
- 条件内容放在 `Condition Block`：一个「限定条件组个数」+ `ConditionBlocks` 列出允许触发的情形（人类条件、魔人条件、拿在手上……），并占一个 `size`（示例：3 种条件 = 108 字节）。
- `Index Count` 表示各条件下触发效果的个数（示例 9 个）。
- **本质：这不是脚本，而是一张"条件 → 特效索引"的映射表。** 索引以特效在文件里的位置为基准。

**第二类：生命周期触发（PtLife）**
- `ukn3 = 0` → 与父特效同时触发；`ukn3 = 3` → **父特效消亡时触发**。
- **关键约束**：消亡触发只认 `Life` 的 `Duration`，`FadeOutDuration` **被完全忽略**。想调触发时机，改 `Duration`，不要改那个名字最像的字段。
- 联动：若要让子特效"像骨骼一样跟随父特效"，需 `ParentOptions` 的 `FollowBone = 1`（见 `efx-bone-parenting`）。

**第三类：碰撞触发（PtColliderAction / PtCollision）**
- `PtColliderAction` 的 `ukn2 = 8` → 碰撞后父特效立即消失。
- `PtCollision` 的 `ukn8~11` 控制碰撞相关行为。

**新增条件的两条硬纪律：**
1. **粘到末尾，不要插中间**。因为索引以特效位置为基准，中间插入会**平移后续所有索引**，让"条件 → 特效"映射整体错位。
2. **同步两处**：① 限定条件组个数 +1；② `Condition Block` 的 `size` 按插入字节数增加（示例：个数 5→6，size 108→112）。个数与 size 是**两个独立的同步点**，任一处漏改都会让映射表长度与内容对不上。

## A1 — 源素材中的应用 (Past Application)

### 案例 1：用幻影剑验证 ukn 的 0 与 2

- **问题**：确认某个特效为什么"随手触发不了"。
- **方法的使用**：把 `ukn` 在 0 与 2 之间切换做对照。
- **结论**：`ukn = 0` → 只在特定条件下触发（无法随手触发）；`ukn = 2` → 无限制条件，用对应技能即可触发。
- **结果**：确立"没有限制条件的特效直接把 ukn 设为 2"。

### 案例 2：读 efd_wp08 的限制条件表

- **问题**：理解"背上魅影"特效的触发条件。
- **方法的使用**：打开 `efd_wp08_001_001_00.efx`，读出 Condition Block Count = 3、限制条件共占 108 字节；展开看到三类条件——人类条件下触发、魔人条件下触发、拿在手上条件下触发；`Index Count` 显示各条件下触发效果个数（如 9 个）。
- **结论**：建立起"条件表 = 若干条件 + 对应触发效果索引"的读法。
- **结果**：知道 108 字节与 3 种条件的对应关系。

### 案例 3：把特效组加入 Condition Block

- **问题**：想让某特效在特定条件下也触发。
- **方法的使用**：找到**最后一个特效组**，Ctrl+Shift+V 粘贴（强调有条件限制的别插中间、建议粘末尾）→ 把条件个数从 5 改为 6 → Ctrl+Shift+L 插入字节 → Condition Block 大小由 108 变为 112。
- **结论**：粘末尾 + 个数 +1 + 插字节 + 同步 size 是完整流程。
- **结果**：进游戏验证——人类状态下切到魅影刀**不触发**，魔人状态下**可触发**，按条件正确工作。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill？

1. 特效**在游戏里怎么都不触发**（"为什么这个特效不出现"）。
2. 想让特效**只在特定条件下出现**（"只有魔人状态才闪""拿在手上才亮"）。
3. 想让子特效**在父特效消失时/消失后出现**（"爆炸之后再冒烟"）。
4. 想做**碰撞触发**（"被打中的时候冒火花"）。
5. 要往带条件的 efx 里**加一个新特效组**，不确定该插哪、要不要改数字。
6. 改了 `FadeOutDuration` 但触发时机**毫无变化**。

### 语言信号（用户的话里出现这些就应激活）

- 中文：「特效不触发」「怎么让它出现」「ukn」「限制条件」「Condition Block」「只能魔人状态触发」「被打中冒火花」「消亡时触发」「ukn 填 0 还是 2」「Index Count」「插在哪」
- English: "effect doesn't trigger", "conditional trigger", "ukn value", "Condition Block", "only in devil trigger", "trigger on hit", "trigger when parent dies", "index count", "where to insert"

### 与相邻能力的区分

- 与 `efx-bone-parenting` 的区别：本能力管**什么时候出现/消失**；那个管**出现后怎么跟随**。触发链里若涉及 FollowBone，只作为依赖声明。
- 与 `efx-safe-structure-edit` 的区别：本能力的"个数 +1 / size 同步"是计数不变量的一个实例；若增删的是普通特效组/属性段，找那个。
- 与 `efx-crash-troubleshoot` 的区别：本能力处理"不触发"这类**逻辑失效**；那个处理"崩了/报错"这类结构故障。注意：编辑器无报错但特效不出来，两者可能都要看。
- 与 `efx-numeric-semantics` 的区别：`ukn` 的数值语义（0/2、0/3）在本能力内解释；通用数值域规则找那个。

## E — 可执行步骤 (Execution)

1. **先判属于哪一类触发**：
   - 按状态触发 → 查 `ukn`（0 有条件 / 2 无条件）与 Condition Block。
   - 按父特效生命周期 → 查 PtLife 的 `ukn3`（0 / 3）。
   - 按碰撞 → 查 PtColliderAction `ukn2`、PtCollision `ukn8~11`。
   - 完成标准：写出"这次是三类中的哪一类"。

2. **读条件表（若涉及状态条件）**：
   - 读「限定条件组个数」与 `Condition Block` 的 `size`；展开 `ConditionBlocks` 看有哪些条件；读 `Index Count` 看触发个数。
   - 完成标准：能复述"有 N 种条件、占 M 字节、对应哪些触发"。

3. **新增/修改条件**：
   - **粘到最后一个特效组之后**（绝不插中间）。
   - 同步：① 个数 +1；② `Condition Block` size 按插入字节增加。
   - F5 重解析，确认无 `*ERROR`。
   - 完成标准：个数与 size 都更新、变量树无报错。
   - 判停条件：若已插在中间 → **先撤出、改为末尾追加**，不要试图"顺便平移索引"。

4. **处理消亡触发的字段陷阱**：
   - 要调"父特效消亡时触发"的时机 → 改 `Life` 的 `Duration`，**不要**改 `FadeOutDuration`。
   - 若子特效需要跟随父特效 → 确认 `ParentOptions` 的 `FollowBone = 1`。
   - 完成标准：触发时机可用 Duration 解释。

5. **进游戏按条件实测**（状态条件必须实测，因为无法离线推演）。
   - 完成标准：各条件下"该触发的触发、不该触发的不触发"。
   - 判停条件：若出现"该触发的没触发 / 不该触发的触发了" → 回到步骤 2 检查索引是否被平移。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 要配的是"**跟随哪个骨骼**" → 用 `efx-bone-parenting`。
- 增删的是普通结构（非条件表） → 用 `efx-safe-structure-edit`。
- 已经崩溃或编辑器报错 → 先用 `efx-crash-troubleshoot` 分流。

### 源素材中警告的失败模式

- **把新特效组插在中间** → 条件表的索引整体平移，触发关系全乱（表现为"该触发的不触发"）。
- **只改了个数、没改 Condition Block 的 size**（或反过来） → 映射表长度与内容对不上。
- **把 `ukn = 2` 理解成"2 个条件"** → 实际是"无限制条件"，语义完全反了。
- **用 FadeOutDuration 调消亡触发时机** → 完全无效，触发只认 Duration。
- **PtColliderAction / PtCollision 的 ukn 值填错** → 碰撞行为与预期不符（这两组 ukn 的多数取值作者也未逐一测明）。

### 作者的盲点 / 局限

- `PtCollision` 的 `ukn8~11`、`PtColliderAction` 的多数取值，作者**未逐一验证**，本能力只主张"8 = 碰撞后父特效立即消失"这一条。
- "消亡触发只认 Duration"是作者的观察结论，机制未解释。
- 条件种类的**完整清单**（除人类/魔人/拿在手上外还有哪些）作者未列全。
- 只验证 DMC5；条件种类与游戏机制强绑定，**不可外推到其它游戏**。

### 容易混淆的邻近方法

- **条件触发（状态） vs 消亡触发（生命周期） vs 碰撞触发**：三者的判断量分别来自"角色状态""父特效时长""碰撞事件"，别混。
- **`ukn` 的两种语义**：同一字段名，0/2（状态条件）与 0/3（生命周期）取值含义不同，靠**所在段**区分，不能只靠字段名。
- **个数 vs size**：Condition Block 的两个独立同步点。
