## I — 方法论骨架 (Interpretation)

在动第一个字节之前，先建立三条纪律。它们不产生功能，但决定了"出错时能不能退回"和"改动能不能被解释"。

**纪律一：备份——因为 `natives` 会随卸载消失**
编辑成果存放在游戏根目录的 `natives` 文件夹里，而它是 **MOD 的挂载层**：**卸载 MOD 会把整个 `natives` 目录一并删除**。所以几乎每次会话都应遵守：
> 改完 → 立刻复制一份到游戏目录之外 → 再继续折腾。
把它当"普通工作目录"是最常见的致命误解（"文件当然在硬盘上"——它在，但生命周期绑定在 MOD 安装状态上）。

**纪律二：环境——路径不要有中文**
010 Editor、EFX.bt 模板、示例 efx 文件的路径都避免中文。工具链（010 Editor、模板脚本）对路径的处理对中文不友好，会引发**无法归因**的读写/模板执行异常。这是一条"用环境整齐换掉一整类诡异错误"的低成本前置项。

**纪律三：认知——不把 `ukn` 当已知字段盲改**
这套模板与字段名是**社区逆向反推**的产物，不是官方 schema。大量字段被命名为 `ukn`、或作者明确标注"未确定/不明"。
"未知"**不代表"无作用"**，只代表"没人测出来"。盲改未知字段等于在未建模的因果系统里掷骰子：
- 无效果 → 让人不断加码；
- 有副作用 → 因缺乏解释而**不可复现**。
所以正确姿势是：改之前先扫一遍要动的地方，遇到 `ukn` 就标记"未证实、改动不可归因"，**不把它当已知参数用**。

**配套的一条最小改动纪律**：本方法论**没有离线校验器**，唯一验证手段是"改完保存 → 重进关卡 → 游戏内观察"。因此标准节拍是**一次只改一处**，才能把结果准确归因到刚改的字段（见 `efx-crash-troubleshoot`）。

## A1 — 源素材中的应用 (Past Application)

### 案例 1：natives 的生命周期

- **问题**：作者在教程开头提醒一个社区里反复发生的损失。
- **方法的使用**：把"修改完成 → 卸载 MOD 前复制一份出来保存"写进前言第一条。
- **结论**：`natives` 是 MOD 挂载目录，卸载即回收，不是普通工作目录。
- **结果**：确立了"先备份、再折腾"的操作纪律。

### 案例 2：路径中文引发的莫名错误

- **问题**：工具链在某些环境下报错但文件本身没问题。
- **方法的使用**：作者把它列为"注意事项"之一——所有软件与文件的路径最好不要有中文。
- **结论**：中文路径是低成本、高收益的规避项。
- **结果**：成为开场检查单的一项。

### 案例 3：EmitterShape3D 的 12 个值

- **问题**：模板里有一组语义不明的值。
- **方法的使用**：作者"测了好久，发现好像只有编号 0 有影响"。
- **结论**：这是**观察**，不是规格——其余 11 个值"好像没什么用"不等于"确实无作用"。
- **结果**：这类字段被本方法论统一归入"不得当已知参数盲改"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill？

1. **准备开始改 MOD**，想先知道"要提前注意什么"。
2. 改好的文件**只在游戏的 `natives` 里**，准备换 MOD / 重装游戏 / 清理 MOD——**成果有丢失风险**。
3. **卸载 MOD 后文件不见了**，或不确定改动放在哪才安全。
4. 遇到**说不清原因的报错**（模板执行失败、文件读不了），想排查环境问题。
5. 看到一堆 `ukn` / "不明"字段，**想凭猜测填值试试**。
6. 想确认"改这个未知字段会不会有风险"。

### 语言信号（用户的话里出现这些就应激活）

- 中文：「改之前要注意什么」「natives 文件夹」「卸载 MOD 会删掉吗」「文件丢了」「路径中文」「模板报错看不懂」「ukn 是什么」「这些未知字段能改吗」「备份」
- English: "before I start modding", "natives folder", "will uninstalling the mod delete it", "lost my files", "chinese path", "template error", "what is ukn", "can I change unknown fields", "backup"

### 与相邻能力的区分

- 与 `efx-safe-structure-edit` 的区别：本能力是**动手前的纪律**；那个是**动手时的结构同步规则**。
- 与 `efx-crash-troubleshoot` 的区别：本能力负责**预防**（备份、环境、心智）；出了故障再分流找那个。
- 与 `efx-numeric-semantics` 的区别：本能力说"`ukn` 不要盲改"；那个提供"已知字段怎么填值"的速查表。两者在 `ukn` 上互补：一个划禁区，一个给安全区。
- 与 `efx-file-structure-model` 的区别：本能力是操作层面的纪律；那个是理解文件层级的地图。

## E — 可执行步骤 (Execution)

1. **开工前：确认备份位置**
   - 确认当前文件在哪里（游戏 `natives` 还是自建工作目录）。
   - 若在 `natives` → **立刻复制一份到游戏目录之外**，作为基线。
   - 完成标准：存在第二份副本，且路径在游戏目录之外。

2. **检查环境**
   - 010 Editor、模板 `.bt`、资源文件的路径**全路径**无中文。
   - 完成标准：路径逐级检查通过；若有中文 → 迁移到纯 ASCII 路径后再开始。

3. **动手前扫描要改的区域**
   - 列出本次要动的字段，把每个标为**已知**或**ukn/不明**。
   - 完成标准：产出一张"已知 / 未知"清单。
   - 判停条件：**若关键改动只能落在 ukn 字段上 → 停手**。要么换方案，要么明确接受"结果不可归因、不可复现"。

4. **建立最小改动节拍**
   - 一次只改一处 → 保存 → F5 → 重进关卡观察 → 记录结果。
   - 完成标准：每次观察都能对应到唯一一次改动。
   - 判停条件：若一次改了几处而结果异常 → 回退到最近一次"单处改动"的状态重来。

5. **收尾：再次备份**
   - 阶段性成果立刻复制出去（不要攒到最后）。
   - 完成标准：最新成果在 `natives` 之外有副本。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已经出了具体故障（`*ERROR`、崩溃、特效不出现） → 用 `efx-crash-troubleshoot`。
- 要查的是"某个已知字段怎么填" → 用 `efx-numeric-semantics`。
- 要查的是"文件层级怎么理解" → 用 `efx-file-structure-model`。

### 源素材中警告的失败模式

- **成果只存在于 `natives`** → 卸载 MOD 时整体删除，不可恢复。
- **路径含中文** → 模板执行/文件读写异常，报错难以归因。
- **把 `ukn` 当已知字段盲改** → 无效果（持续加码）或不可复现的副作用（甚至崩溃）。
- **"先填个大数试试"** → 典型盲改心理，制造不可归因的结果。
- **一次改多处再验证** → 结果无法归因到具体字段。

### 作者的盲点 / 局限

- "路径不要有中文"作者**未给具体报错**，是经验性规避建议。
- 作者对大量字段公开承认"未确定"，因此**本能力无法给出这些字段的安全取值**——只能划禁区。
- 只针对 DMC5 的 MOD 工作流；其它游戏的挂载机制**无素材证据**。

### 容易混淆的邻近方法

- **"备份" vs "版本控制"**：本书只有"复制一份"这一条手段，不涉及 git 等。
- **"环境问题" vs "文件问题"**：同样报错，先排除环境（路径、模板）再看文件内容。
- **"未知字段" vs "字段名奇怪但已知"**：判断依据是**作者/C 是否标注过**，不是"名字像不像人话"。
